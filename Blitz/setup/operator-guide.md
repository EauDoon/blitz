# Using Blitz v2.1OAI-r1 in Blitz

Describe the result you want. You do not need a command, skill name or setup ritual. Blitz should gather accessible information, make the requested output, check that it is usable and preserve what is needed to continue it.

| What you want | An ordinary request | What should happen |
|---|---|---|
| Start substantial work | "Prepare an investment note and workbook for the finance team using these sources." | Select or start one item, retrieve required authorized inputs, populate the outputs and check content and calculations. |
| Continue existing work | "Pick up the finance note and finish the sensitivity analysis." | Recover its current revision and accepted decisions, then continue the same item. A stale tracker does not require another decision. |
| Make a small edit | "Make this paragraph shorter." | Return the edit with proportionate checking. No project pack or interview. |
| Think before acting | "Only plan the reporting process." | Return the plan. No implementation or deployment. |
| Review without changing | "Review this workbook for errors. Do not edit it." | Inspect and explain findings. The file remains unchanged. |
| Repair commissioned work | "Fix these errors and check the revised file." | Repair within the named scope, recheck affected results and deliver the revised artifact. |
| Move an item out | "Package this item so I can continue it in another project." | Produce an allowlisted bundle with editable work, evidence, state, selected methods and a README. Destination changes still need authority. |
| Develop a receiving copy | "Use this bundle to make a working copy here and revise the conclusion." | Verify identity and dependencies, create authorized local lineage/revisions and preserve Blitz's original. |
| Transfer ownership | "Make this receiving project the canonical owner of this item." | Record the named ownership transfer and mark the former canonical copy historical, within granted access. |
| Stop | "Pause here" or "Cancel the send." | Stop the affected work. Resume never silently revives a canceled action. |

## When Blitz should ask you

Only when a consequential outcome or item is ambiguous, needed information cannot be retrieved in scope, access/authority is missing, or a decision is reserved for you. It should ask for the smallest missing input and continue useful independent work. A broad questionnaire is not required. If several choices matter, expect a recommendation, strongest alternative and consequence, not another administrative queue.

## What a finished result should include

The requested answer or accessible artifact comes first. Required data should already be populated from readable evidence. Material arithmetic and applicable rendered files should have been checked. Necessary assumptions and missing dependencies should be explicit. A blank template is complete only when you requested a blank template. A draft is not sent, and an exported ZIP is not installed, merely because it was prepared.

Short work can stay in the chat. Substantial work may need a stable item ID, current files and enough saved state to resume. The existing 00/03/09/10 records remain available, but Blitz should not fill empty templates or update trackers without a useful reason.

## Take an item elsewhere

1. Ask for an export of the named item. Specify a destination or format if it matters. Blitz checks the allowlist, necessary evidence and resources, editable originals, revisions and archive integrity.
2. Open the bundle's README in the receiving environment. Supply its readable PROJECT_INSTRUCTIONS.md and needed files if that environment cannot read ZIPs. Credentials and account access are never carried in the bundle.
3. State the receiving task, for example: "Use this bundle to make a working copy here, then update the cost sensitivity." The receiver should identify the governing decisions, check dependencies, perform the authorized change, save it and resume from the saved result.

Blitz stays the canonical original unless you explicitly transfer ownership. Work on a receiving copy can progress independently under its own authorized revisions. It must not silently update Blitz or merge conflicting positions. A missing required tool or external source remains a named dependency.

## Recover an interrupted task

Say which item to resume. Blitz should recover its current artifact and relevant decisions, then inspect receipts or resulting state before repeating any uncertain action. It should not replay a completed send or revive a cancellation. If the save route was unavailable, provide the last versioned state bundle; Blitz should say exactly what is still unsaved.

For configuration rollback, use the release/application receipt and the matching verified rollback archive. Restoration is a separate authorized action against named targets. Do not paste a historical register over a newer release or restore unrelated deleted work by assumption.

## What stays final

Blitz v2.1OAI-r1's operating method is frozen. Your items, evidence and requested outputs continue to evolve without upgrading Blitz. No periodic maintenance ritual, account-wide skill installation or background service is needed. Work remains available and outside skills/instructions stay unchanged. This is project-scoped behavior, not a claim of memory isolation.

External tools and platforms may change. Blitz should check what a task needs, use a sufficient supported fallback or state the exact limit. The release receipt records what was actually tested; no system can promise permanent compatibility or universal freedom from bugs.

For operating details use [the contract](operating-contract.md); for resource loading and export mechanics use [the Blitz adapter](source-use.md).
