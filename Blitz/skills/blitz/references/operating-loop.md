# Operating Loop

Optional Blitz module. Use within the selected Blitz profile and current task authority. This module adds no applied system, skill installation, mandatory record, inbox, or review schedule.

## Purpose

Continue useful work from what has actually happened. the owner may have made a decision without updating a tracker because the update was unnecessary. Recover the applicable decision; do not confuse stale tracking with indecision or turn record reconciliation into a new project.

## When to use it

Use on a relevant transition: resuming work, handing off a consequential outcome, revising a material position, resolving a dependency, checking follow-through, or recovering an uncertain action. Also use when conflicting state would change the requested outcome.

Skip the module when the request is unrelated, the current context is already sufficient, or no useful follow-through remains. It is not a mandatory daily review, end-of-response routine, or sweep of every open item.

## One useful pass

1. Identify the requested outcome and read only relevant accessible context. Recover prior explicit decisions with their source, scope, conditions, and authority. Distinguish a reported agreement from independently verified evidence. New timestamps do not automatically replace adopted decisions.
2. Determine what affects the next action: an applicable ruling, a real unresolved choice, missing evidence, an authorized action, a dependency, or a review finding. These may be linked parts of one outcome; do not create a queue for each category.
3. Continue from settled decisions. Ask again only for a material ambiguity, changed scope, genuine conflict, or missing authority. A stale row alone does not justify a question, repair assignment, or write.
4. If the next result needs missing factual inputs, use [context acquisition](context-acquisition.md): retrieve and extract relevant authorized sources, then populate the result. Do not turn sufficient context or a narrow edit into a search. Prepare only the next useful result. For a decision that genuinely needs the owner, give the recommendation, strongest alternative, consequential tradeoff, cost of waiting or reversing, and the action approval would permit. Use qualitative costs when no estimate is supported. Silence and acknowledgment alone are not approval.
5. Complete authorized work and verify the outcome at the relevant surface, including its required substantive content. Keep a ruling, prepared output, saved version, delivery, and acceptance distinct. Use the existing proportional review contract; this module does not create another quality gate.
6. Preserve only consequential state that a future consumer needs, within current authority and the existing canonical-write contract. Return the usable result and any consequential uncertainty, then stop.

## Persistence test

Write when at least one concrete need exists: a future action or output would otherwise use the wrong position; a handoff would lose material context; recovery could repeat a consequential action; a standing obligation requires a receipt; or the user explicitly requested the record update. Write the minimum sufficient change where it already belongs.

Do not write solely to make a tracker tidy, mirror a decision already available to the relevant consumer, produce an empty DELTA, or satisfy a per-interaction reporting ritual. If no useful record change exists, finish without one. Do not announce the absence of bookkeeping unless it matters to the user.

Within this module, stage-line updates, capture blocks, daily records, DELTAs, and checkpoints are conditional on a useful material change or an applicable explicit requirement. This does not waive mandated release/pilot evidence, required receipts, or the safety of an actual canonical write. Full meeting extraction and comprehensive-profile deliverables remain available when requested or required by the selected outcome.

Keep the four mandatory Blitz record names and purposes. Update only the relevant record, never all four as a routine:

- `00 Read Me First.md`: governing project context, canonical locations, authority, or acceptance criteria when they change.
- `03 Position Of Record.md`: consequential changes to the supported current position. It is not a task diary.
- `09 Open Questions.md`: genuine unresolved questions and evidence needed for the work. An old open row does not undo an applicable explicit ruling.
- `10 Decision Log.md`: consequential explicit rulings or events that need durable history. Preserve the existing append-only history when a change is recorded.
- Existing task records or an authorized action tracker: execution, relevant dependencies, accepted ownership, checkpoints, and result evidence. Link to the ruling rather than duplicating it.

A material update that is useful but cannot be saved under current authority remains an unsaved proposed change or minimal handoff. Identify the exact unavailable destination or authority only when it affects the requested outcome. Do not claim the change was saved.

## Follow-through and recovery

An accepted owner requires explicit acceptance or applicable standing responsibility. A model naming a colleague creates only a proposed assignment. An internal review checkpoint is not an externally agreed deadline. Require owners, dependencies, and timing only when relevant; do not invent them.

Honor explicit cancellation. A canceled send remains canceled even if a tracker still says pending. A possible unresolved external misunderstanding may remain an exposure; it does not grant permission to reopen or send the canceled action. Preserve cancellation where necessary to prevent accidental execution.

Before retrying an interrupted write, inspect its receipt or resulting state. If completion remains unknown, keep the uncertainty and avoid an unsafe duplicate. A missing checkpoint is not proof that the underlying work failed; use sufficient accessible source and resulting-state evidence. Do not invent missing history. Hold only work whose required basis remains unavailable.

Use the established unique DELTA, expected-revision, duplicate, conflict, and one-writer safeguards whenever a canonical write is needed. Do not create a DELTA when nothing needs changing. Preserve live obligations across document replacement unless fulfillment, explicit cancellation, or an authorized replacement is supported.

Set closure evidence to match the requested outcome. A sent message does not establish agreement; acknowledgment is required only when the outcome calls for it. Inspect only authorized sources and state their coverage limits. Absence from accessible sources does not prove no obligation exists.

## Return to Blitz

Route substantial production, changed scope or mandate, material source conflict, or reopened readiness to the relevant existing Blitz workstream and stage. Continue unaffected authorized work. Keep the same canonical records, owner, profile, and permissions. A second host or specialist returns a scoped proposal against its input revision, not a parallel canonical position.

The module works without `operating-cadence`, `decision-os`, or `memory-keeper`. Use an available compatible method only after checking its role and actual host availability. Do not create their legacy stores or assume access because a bundled skill names them. Map needed functions to the authorized current records.

## Output and limits

Respond in the requested format. Usually give the useful result, next consequential dependency if any, and the actual completion state. Do not require five empty blocks, a status card, or a decision agenda for a narrow continuity request. If a review was requested, prioritize consequential choices without hiding genuine obligations or letting older deferred work disappear.

An attached package does not establish installation, native loading, automatic routing, adoption, or background monitoring. Explicit module trials establish only their observed behavior. Judge usefulness by reduced repeated consequential work and successful continuation or handoff, not record-update counts.
