# Blitz v2.1OAI lean profile

## Purpose and selection

Use for bounded project setup, research, review, repair or delivery that does not need a full operating pack. Lean is the default when no comprehensive pack is commissioned. [The operating contract](../setup/operating-contract.md) owns this ordinary path. This profile changes process size, not source, privacy, authority, revision, recovery or acceptance gates. Keep the established state vocabulary; ordinary work needs no stage progression. Timed pilot/setup mechanics apply only when selected. Assess readiness from evidence, not elapsed hours.

## Minimum useful process

- One owner, one workstream and the requested deliverable initially. One person may be the coordinator and canonical scribe; independent review is separate when the stakes require it.
- Keep `00 Read Me First`, `03 Position Of Record`, `09 Open Questions` and `10 Decision Log` with their existing names and schemas when useful state is needed. Reuse existing fields for profile selection, agreed pack and acceptance references. Create no empty tree for short work. An empty question list is valid; an unconfirmed baseline is labelled PROPOSED rather than adopted.
- A commission can be compact and inline when no work is delegated. Preserve the commission's outcome, audience, format, governing revision, dependencies, permitted writes and acceptance criteria. Infer reversible defaults only when they do not change authority or consequential choices.
- Use written task instructions or an existing authorized decision to confirm scope. A meeting is needed only to resolve material intent or coordination gaps. If a meeting occurs, use the call/capture/debrief procedures, and preserve decisions versus proposals.
- Produce one canonical artifact in the requested format. When format is unspecified, use the smallest usable supported format appropriate to the request, recording the choice in the commission. Do not create both a Google Doc and DOCX merely to satisfy a default. A final requested DOCX, converted Doc, deck, spreadsheet or visual still needs its applicable native render and verification workflow.
- Observe only applicable capabilities. Read-only observations can reuse current evidence for the same host/configuration. Unneeded rows are `not tested / not applicable to this task`, never works. No probe authorizes an external write, account change, upload, installation or broader access.
- Add a workstream, artifact, tool, specialist, meeting or evaluation round only for an identified dependency, risk or requested output. Record why. No minimum of five workstreams is imposed. The five to eight map is a comprehensive planning heuristic for projects that actually need those owners/outputs.

Use [context acquisition](../skills/blitz/references/context-acquisition.md) when required inputs are missing. Retrieve and apply relevant authorized evidence before dependent production; verify required content in the actual artifact. No extra form, broad search or new permission follows.

## Unchanged gates

1. Scope before project facts or tools; keep private-lane data and source instructions outside build-lane authority. Only allowlisted build files may leave the canonical store; PRIVATE files never enter a shared pack.
2. Source-to-claim lineage: each factual claim names its actual evidence source and passage, status, scope and as-of time. Keep the briefing/context source separate from evidence cited for a load-bearing claim. A source title, issuer name or remembered summary alone does not verify a claim. Missing/unreadable evidence remains UNVERIFIED; hold only conclusions that depend on it.
3. the owner's current instructions and the one adopted file 03 baseline govern their scope. New evidence may challenge a decision but cannot adopt a replacement. Record revisions and mark affected outputs stale or refresh them.
4. One canonical scribe, expected revision and unique DELTA IDs. Duplicate IDs create no duplicate revision; conflicting reuse is rejected and retained for review. Reread and reconcile stale sources before writing.
5. Actual verification evidence, not assurances. Material arithmetic runs in code. Apply proportional independent review and rendered-artifact checks when the task or stakes require them. Project skills are optional and retain their own release gates.
6. Preserve necessary checkpoint and handoff state; inspect uncertain writes before retrying. Continue from confirmed result identities, outstanding DELTAs and the next authorized action. Never replay a completed external write.


Source fidelity: use the actual evidence source, and only the current task/scenario sources for their stated subjects. If a source does not specify its subject, retain that uncertainty; never fill it from another batched scenario, prior output or memory. Name source IDs without assigning an unsupported subject.
## Completion

Finish when the requested outcome meets its acceptance criteria, applicable checks are complete, the usable result and necessary recovery state are saved, and consequential uncertainties are explicit. A blocked outcome retains useful partial work plus the exact blocker. Do not continue adding outputs to fill stage windows. Real adoption still requires representative outcome evidence, demonstrated recovery, the owner's acceptance and applicable host checks. Lean trials cannot establish speedup, automatic routing, installation or cross-host compatibility.

Use the optional [Operating Loop](../skills/blitz/references/operating-loop.md) for relevant continuity. Recover settled decisions before asking again. Persist only consequential execution, handoff or recovery state, or explicitly required evidence. Existing source/result evidence can suffice without a new checkpoint or DELTA. Preserve the full commissioned pack, mandated pilot/release evidence and all actual-write safeguards.
